# Dialog SFT Forge 架构说明

## 1. 项目定位

Dialog SFT Forge 是一个“数据工厂型”系统，用于把业务话术模板、用户案例和概率路径逻辑，合成为高质量对话训练样本。它不是单纯的对话生成脚本，而是面向 SFT 数据闭环设计的工程化框架。

从设计上看，它具备以下三层目标：

1. 让业务人员只关心内容：案例、话术模板、条件表达式。
2. 让工程人员只关心流程：配置加载、路径生成、条件评估、对话拼装。
3. 让训练团队拿到稳定、可复现、带 trace 的样本数据。

## 3. 模块职责

### 3.1 data 层

目录：`scripts_general/core/data/`

核心职责：

- 从 Excel 读取模块话术表
- 从概率矩阵中恢复模块列表
- 从 text case 中解析字段和值
- 抽取 prompt 与 scenario 语境

关键模块：

- `data_loader.py`
  - `load_sheets()`：按模块名读取表格
  - `load_prob_matrix()`：从 `.xlsx` 概率矩阵中建立模块索引
  - `parse_case_info()`：解析 `- 字段：值` 的 case 文件
- `case_generator.py` / `prob_generator.py`
  - 负责生成示例数据与概率表初始化逻辑

### 3.2 generation 层

目录：`scripts_general/core/generation/`

核心职责：

- 路径生成：根据概率矩阵随机遍历模块
- 对话组装：按路径选择合适的话术，填充占位符
- 断点续传：记录已生成样本与缓存状态
- trace 追踪：保留模块选择、条件匹配和回合信息

关键模块：

- `path_generator.py`
  - `PathGenerator.generate_one()`：生成单条模块路径
  - `PathGenerator.generate()`：批量生成路径缓存
- `dialogue_builder.py`
  - 承接路径、案例和话术表
  - 负责最终对话输出拼装
- `parallel_generator.py`
  - 统一单/多进程生成流程

### 3.3 conditions 层

目录：`scripts_general/core/conditions/`

这是整个系统“业务条件驱动”的关键点。

核心职责：

- 把条件表达式解析成原子判断
- 支持多条件组合（如 `A & B & C`）
- 对 case 的字段值执行校验
- 输出可解释的条件描述和匹配元数据

关键模块：

- `parser.py`
  - `ConditionParser.parse()`：把字符串条件拆成 token 并求值
  - `ConditionParser.evaluate_with_metadata()`：返回解释性日志
- `numeric_compare.py`
  - 数值比较条件，如 `积分余额 > 1000`
- `field_nullability.py`
  - 检查字段 null / empty / exist
- `unknown.py`
  - 未识别 token 的兜底处理

### 3.4 pressure 层

目录：`scripts_general/core/pressure/`

核心职责：

- 组织促销话术
- 管理 `repeat(次数)`、`parent(继承)` 与 `flexible_stop(可选不继承)`
- 把“业务促销插入”融入正常模块链路

关键模块：

- `pressure_manager.py`
  - 在某个模块中随机插入一段促销或跟进话术
  - 处理祖先链与后代链的组合

### 3.5 utils 层

目录：`scripts_general/core/utils/`

核心职责：

- 随机服务：统一种子与随机决策
- 时间生成：模拟自然语言时间
- 路径缓存：避免重复消耗
- 日志与 trace：便于复盘

### 3.6 analysis 层

目录：`scripts_general/core/analysis/`

核心职责：

- 衡量条件覆盖率
- 统计模块多样性
- 检查路径偏斜和热点条件
- 输出分析图和报告

## 4. 依赖方向

最重要的依赖关系可以概括为：

```text
config / excel / case
        │
        ▼
data loader ───────► generation
   │                  │
   ▼                  ▼
conditions ───────► dialogue_builder
   │
   ▼
pressure_manager ───► dialogue_builder
```

说明：

- `data loader` 负责把原始资源转换成可用数据结构
- `conditions` 提供判定逻辑，供路径和话术选择调用
- `generation` 负责路径 + 对话拼装
- `pressure` 作为扩展策略，插入更真实的促销或复购节奏
- `analysis` 侧重对已生成结果做诊断，而不是直接参与主生成流程

也就是说，整个设计遵循“输入 -> 解析 -> 选择 -> 拼装 -> 输出”的单向依赖，避免把不同层次逻辑耦合在一起。

## 5. 核心设计：FSM 路径生成

概率矩阵的核心思想是：

- 每个模块都是一个状态
- 每个状态有到其它模块的转移概率
- 路径生成过程即状态转移过程

### 5.1 状态机约束

配置中常见的约束包括：

- `start`：初始模块
- `terminal_modules`：终止模块
- `a_set` / `b_set`：用于控制分支约束
- `self_loop_modules`：允许模块重复出现

`PathGenerator.generate_one()` 会依据这些规则来筛选候选节点并随机选择下一跳，保证生成路径符合业务剧本。

### 5.2 为什么用概率矩阵

概率矩阵的价值在于：

- 业务规则可以被“表格化”
- 生成逻辑与业务语义分离
- 模块组合可直接被分析、审计和调优

## 6. 核心设计：条件注册表

条件系统的设计理念是“原子条件 + 组合解析”。

### 6.1 原子条件

每种条件都实现一个最小判定能力，例如：

- 数值比较：`消费金额 > 100`
- 是否为空：`字段为空` / `字段非空`
- 未知 token：兜底保守处理

这些原子条件都继承自 `AtomicCondition`，并在注册表中被统一调用。

### 6.2 组合逻辑

条件字符串通常是：

```text
积分余额 > 1000 & 是否会员 = 是 & 订单金额 > 50
```

`ConditionParser` 会将它切成多个 token，再逐个判断；最终用逻辑与 (AND) 联接，保证只有满足所有条件的样本才会被当前模块命中。

### 6.3 可扩展性

新增条件类型时，只需：

1. 实现 `AtomicCondition` 子类
2. 注册到 `ConditionParser`
3. 在 Excel 表中使用对应条件文本

这样能保持核心解析逻辑稳定，扩展成本很低。

## 7. 核心设计：继承链与话术自然展开

模块话术并不是简单地随机抽取，而是以“继承链”为主线重组对话。

### 7.1 parent(继承)

每个模块话术行都可能声明它的父级节点，形成一条祖先链。`get_ancestors()` 会沿着链条向前回溯，恢复前置上下文。

### 7.2 descendant chain

`get_random_descendant_chain()` 会根据条件和概率随机选择后续的衍生话术，构成自然延续。

### 7.3 flexible_stop

如果某一行设置了 `flexible_stop(可选不继承)`，系统可以在随机概率下提前停止继续展开，从而模拟更真实的对话收束过程。

这使得生成的对话不只是“模板拼接”，而是更接近真实客服/运营事件流程。

## 8. 运行流程

整个生成流程可以整理成如下顺序：

1. 加载配置：读取 YAML / 任务参数
2. 加载概率矩阵：得到模块集合和状态转移图
3. 加载案例：读取业务字段与 prompt
4. 生成路径：按概率矩阵随机生成模块路径
5. 条件过滤：根据案例字段匹配模块条件
6. 话术选择：按继承链 + 促销策略 + 话术模板取值
7. 组装对话：填充占位符并拼接 messages
8. 存储输出：写入 JSON / trace / analysis

## 9. 工程特点与设计收益

### 可维护性

- 业务配置与代码逻辑分离
- 数据表格可由非程序员维护
- 生成流程稳定，便于持续迭代

### 可扩展性

- 新增条件类型只要注册即可
- 新场景只需要写新 Excel 与 case 文件
- 支持单/多进程、增量批量生成

### 可追踪性

- 每次生成都可保留 trace
- 能看到模块选择、条件命中、路径选择过程
- 更适合对数据质量做诊断和迭代

### 可复现性

- 固定随机种子
- 缓存路径
- 一致配置 -> 一致结果

## 10. 适用场景

本项目最适合以下业务场景：

- 客服回访
- 会员关怀
- 促销活动跟进
- 商务联络和售后问询
- 需要多轮状态流转的对话任务

如果业务要求“对话结构有状态、场景有分支、依赖随数据变化”，那么这个框架就是一个天然的基础设施。
